# Complete rewrite: Node.js/Express + React family tree application

This change replaces the Kotlin/Micronaut/Neo4j starter with a full-stack JavaScript application. The server uses Express with Knex/SQLite and exposes REST endpoints for person CRUD, relation management, and recursive tree traversal. The client uses React with TypeScript, React Router for navigation, and React Flow (@xyflow/react) for graph visualization. The architecture is straightforward: a Vite-proxied dev setup where the client talks to `/api` routes on the Express backend.

Watch for: The client and server disagree on the ID type for all entities (confirmed) — the server generates UUID strings, but every client type declares IDs as `number` and passes them through `Number()`. The tree API returns `ancestors`/`descendants` fields but the client's `TreeNode` type expects `parents`/`children` (confirmed), which will silently produce empty trees. The relation categorization in `GET /persons/:id` sends the raw DB relation type in the response payload instead of the contextually-correct flipped type (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The ID type mismatch is a system-wide contract failure. The server uses `uuid` for every primary key (persons, names, relations) and returns them as strings. The client declares all IDs as `number`, casts route params with `Number(id)`, and compares them with `===`. Since `Number("some-uuid")` is `NaN`, every comparison fails, person detail pages won't load, and relations can't be created from the UI.

The tree API returns recursive structures with `ancestors` and `descendants` arrays, but the `AncestryView` component reads `node.parents` and `node.children` from the response. These fields are always `undefined`, so the ancestry graph renders a single root node with no connections.

Relation resolution in the person detail endpoint correctly buckets relations into parents/children/spouses, but the `RelationView` object it sends to the client carries `rel.relation_type` (the raw DB value) rather than the contextually-flipped type. The client sees "parent" or "child" from the wrong perspective on inverse relations.

The `createRelationWithPerson` endpoint always puts `existingPersonId` as `from_person_id`. This produces correct directional records for the currently-viewed person's tree traversal, but tree traversal starting from the *newly created* person finds no relations — because no symmetric record exists and the tree queries only follow `from_person_id`.

<details>
<summary>Issues (7)</summary>

1. **ID type mismatch across the entire client** — Server returns UUID strings for all entity IDs; client types declare them as `number` and casts with `Number()`, producing `NaN`. Change all client ID types to `string` and remove `Number()` casts.
2. **TreeNode field name mismatch** — Server tree endpoints return `ancestors`/`descendants`; client `AncestryView` reads `node.parents`/`node.children`. Align field names in either the server response or the client component.
3. **`RelationView` carries raw DB relation type** — `GET /persons/:id` flips `relationType` for bucketing but sends `rel.relation_type` (unflipped) in the response object. Use the flipped value so the client displays the contextually-correct label.
4. **Unidirectional tree traversal from new persons** — `createRelationWithPerson` always stores `existingPersonId` as `from_person_id`. Tree traversal from the newly-created person finds nothing because queries only follow `from_person_id`. Either create symmetric records or make tree queries bidirectional.
5. **No input validation on person creation** — A POST to `/api/persons` with an empty body or empty names array creates a person with no name. Add validation requiring at least one name with either `givenName` or `familyName`.
6. **`getDisplayName` type doesn't accept `TreeNode`** — The utility's union type is `Person | GraphNode | RelationPerson`, all with `id: number`. After fixing IDs to strings, `TreeNode` still won't satisfy the signature. Broaden the accepted type.
7. **No duplicate relation prevention** — The API allows creating the same relation between two people multiple times. Add a uniqueness check on `(from_person_id, to_person_id, relation_type)`.

## ID type mismatch: UUID strings vs numeric assumptions

The server's `Person` model declares `id: string` and generates IDs with `uuidv4()`. The database schema uses `table.text('id').primary()`. Every response from the server returns IDs like `"a3f2b1c4-..."`.

The client's `types.ts` declares:

```typescript
export interface Person {
  id: number;
  // ...
}
```

Every component that receives a route param does `Number(id)` before passing it to the API:

```typescript
// PersonForm.tsx
getPerson(Number(id))

// PersonDetail.tsx
getPerson(Number(id))

// AncestryView.tsx
Promise.all([getAncestors(Number(id)), getDescendants(Number(id))])
```

`Number("a3f2b1c4-...")` evaluates to `NaN`. The GET requests will hit `/api/persons/NaN`, which returns 404. The `RelationForm` component also sends `NaN` as `fromPersonId`/`toPersonId` in relation creation calls, causing 404s on the server's person-existence check.

## Tree API field name mismatch breaks ancestry graph

The server's `tree.ts` defines:

```typescript
interface TreeNode {
  id: string;
  ancestors?: TreeNode[];
  descendants?: TreeNode[];
}
```

The client's `types.ts` defines:

```typescript
export interface TreeNode {
  id: number;
  parents?: TreeNode[];
  children?: TreeNode[];
}
```

In `AncestryView.tsx`:

```typescript
function processAncestors(node: TreeNode, ...) {
  if (node.parents) {  // always undefined — server sends "ancestors"
    node.parents.forEach((parent, idx) => { ... });
  }
}

function processDescendants(node: TreeNode, ...) {
  if (node.children) {  // always undefined — server sends "descendants"
    node.children.forEach((child, idx) => { ... });
  }
}
```

## Relation categorization sends wrong type label to client

In `routes/persons.ts`, the detail endpoint flips `relationType` for bucketing when the current person is on the `to` side of a relation:

```typescript
if (rel.from_person_id === person.id) {
  relatedPersonId = rel.to_person_id;
} else {
  relatedPersonId = rel.from_person_id;
  if (relationType === 'parent') relationType = 'child';
  else if (relationType === 'child') relationType = 'parent';
}
```

But the `RelationView` sent to the client uses the raw value:

```typescript
const relationView: RelationView = {
  relationType: rel.relation_type,  // original, not flipped
  // ...
};
```

A parent viewing their profile sees children listed under "Children" (correct bucket), but each child's relation tag says "child" — which reads as "this person is a child" from the DB's perspective, not "this is my child". The semantic inversion creates confusing labels in the UI.

## Unidirectional tree traversal

The tree queries in `tree.ts` only follow one direction:

```typescript
// Ancestors: from_person_id = current person, relation_type = 'parent'
const parentRelations = await db('relations')
  .where('from_person_id', personId)
  .andWhere('relation_type', 'parent');

// Descendants: from_person_id = current person, relation_type = 'child'  
const childRelations = await db('relations')
  .where('from_person_id', personId)
  .andWhere('relation_type', 'child');
```

When `createRelationWithPerson` stores `from=existingPerson, to=newPerson`, the new person has no records where they are `from_person_id`. Traversal starting from the new person returns an empty tree. The regular `createRelation` endpoint (used in tests) creates both directions explicitly, but the `with-person` convenience endpoint does not.

## No server-side validation on person creation

The POST `/api/persons` handler casts `req.body` to `PersonCreate` without validation:

```typescript
const body: PersonCreate = req.body;
```

A request with `{}`, `{ names: [] }`, or `{ names: [{}] }` succeeds and creates a person that renders as "Unknown" in every view. The `PersonForm` component has no `required` attribute on name fields, so a user can submit the form with all fields blank.
