# Complete rewrite: Node.js/Express + React family tree application (v2)

This change replaces the Kotlin/Micronaut/Neo4j starter with a full-stack JavaScript application: Express with Knex/SQLite on the backend, React with TypeScript and React Flow on the frontend. The v1 review surfaced 7 issues (ID type mismatch, tree field names, relation type flip, bidirectional traversal, validation, utility types, duplicate prevention). All 7 have been addressed. The fix commit corrects client types to use `string` IDs throughout, aligns `TreeNode` field names to `ancestors`/`descendants`, uses the flipped `relationType` in the response payload, makes tree traversal bidirectional, adds person creation validation, broadens the `Displayable` union type, and adds duplicate relation checks with a 409 response. 28 tests pass including 4 new ones covering the validation and duplication guards.

Watch for: The `with-person` endpoint bypasses both the name validation and the duplicate relation check that protect the direct endpoints (confirmed). The duplicate relation check is directional — swapping `fromPersonId` and `toPersonId` for the same type creates a second record (likely). The `PersonForm` client component sends empty `familyName`/`givenName` strings rather than omitting them, which the server's `trim()` check handles correctly, but the form itself has no required-field indicator for the user (confirmed — minor UX gap, not blocking).

**Verdict**: APPROVED

## High-level view

All v1 contract mismatches are resolved. The client and server agree on `string` IDs, `ancestors`/`descendants` field names, and contextually-correct relation type labels. The tree queries now traverse both directions (`from_person_id` with type X and `to_person_id` with inverse type), deduplicate via a local `Set<string>`, and the `visited` set prevents cycles.

The `with-person` endpoint creates a person without checking for a valid name and creates a relation without checking for duplicates. Both guards exist on the direct `POST /api/persons` and `POST /api/relations` routes but were not replicated here. In practice the client's `RelationForm` uses an HTML `required` attribute on the "Given Name" field when creating a new person inline, so the gap is only exploitable via direct API calls.

The duplicate check on `POST /api/relations` only matches on exact `(from_person_id, to_person_id, relation_type)` tuples. A relation `A→B parent` and `B→A child` represent the same real-world fact but pass the duplicate check independently. The tree traversal handles this gracefully (deduplication via `ancestorIds`/`descendantIds` sets), so it doesn't break anything — it just allows semantically-redundant records.

## Validation gap in `with-person` endpoint

The `POST /api/relations/with-person` handler validates that the existing person exists and that the relation type is valid, but it does not validate the new person's names:

```typescript
// routes/relations.ts, line ~86-94
const newPersonId = uuidv4();
const now = new Date().toISOString();

await db('persons').insert({
  id: newPersonId,
  // ...inserted directly without name validation
});
```

Compare with `POST /api/persons` which checks `body.names.some(n => n.givenName.trim() !== '' || n.familyName.trim() !== '')`. A direct API call to `with-person` with `newPerson: { names: [] }` creates a nameless person.

Similarly, no duplicate relation check runs before inserting. The `POST /api/relations` route queries `db('relations').where(from, to, type).first()` before insertion, but `with-person` inserts unconditionally.

## Directional duplicate semantics

The duplicate check in `POST /api/relations`:

```typescript
const existingRelation = await db('relations')
  .where('from_person_id', body.fromPersonId)
  .andWhere('to_person_id', body.toPersonId)
  .andWhere('relation_type', body.relationType)
  .first();
```

This doesn't account for the semantic equivalence between `A→B parent` (A declares B as parent) and `B→A child` (B declares A as child). The tree traversal queries already handle both directions so this won't produce incorrect tree output, but it does allow duplicate edges in the graph view and double-counted entries in the person detail relations list.

The `RelationForm` client always sets `fromId = personId` regardless of relation type, so from the UI this scenario only arises if two different users add relations from different person pages pointing at each other.

## Update endpoint skips name validation

```typescript
// routes/persons.ts, PUT /:id
if (body.names !== undefined) {
  await db('person_names').where('person_id', req.params.id).delete();
  for (const name of body.names) {
    await db('person_names').insert({ ... });
  }
}
```

When `body.names` is `[]` or contains only entries with empty strings, the existing names are deleted and replaced with nothing. The invariant established at create time (at least one name with `givenName` or `familyName`) is not enforced on updates.
